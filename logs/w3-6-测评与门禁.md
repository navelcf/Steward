\# 二、为什么不能凭感觉，具体举例



\## 场景：你想把 `CHILD\_SIZE` 从 400 改成 300



\*\*凭感觉的做法：\*\*



```

你改完，重启，随便问一句"星云科技收入如何"，

看检索结果，觉得"好像差不多"。

就提交了。

```



\*\*这个做法的问题，逐条：\*\*



\*\*① 你问的那一句，正好是今天运气好的一句\*\*



`top\_k=20` 召回后去重，你看到 6 条。\*\*这 6 条今天排对了，不代表 12 种问法都对。\*\*



\*\*② 你根本没法判断"排第 1 还是排第 3"\*\*



你上一轮实测看到 `0.0325` 和 `0.0325` 并列、`0.0317`、`0.0308`。\*\*这个量纲没有区分度\*\*（你可能还记得——整个区间只有 0.0125\~0.0328，宽 0.02）。\*\*你看这堆数字看不出任何东西。\*\*



\*\*③ 你看不到"变差的地方"\*\*



`CHILD\_SIZE` 变小 → 每块更碎 → \*\*召回更容易命中（recall 涨）\*\*，但 \*\*Med 里塞 6 条拼起来的上下文更碎片化（precision 可能跌）\*\*。



\*\*你只会注意到"能不能查到"，不会注意到"排位掉了"。\*\*



\*\*④ 三个月后你忘了\*\*



你改回 400 的时候，\*\*凭什么？\*\* 你只记得"当初好像 300 更好"。



\*\*⑤ 最要命：你没有任何记录证明你做的判断\*\*



面试官问"你怎么评估检索质量"，\*\*你说"我试了几句感觉还行"\*\*。这等于没答。

\## 第 1 步：改之前，先跑一次基线



```powershell

uv run python scripts/run\_eval.py --label chunk400\_top20

```



\*\*`--label` 是这次跑的名字，必填。\*\* 名字要能看出配置：`chunk400\_top20` = 块 400 字、每路召回 20 条。



\*\*这一跑干了什么（内部 5 件事）：\*\*



```

1\. 读 tests/eval\_cases/rag\_v1.jsonl → 12 个 dict

2\. 循环 12 题，每题调一次 retrieve\_sources（= 1 次 embedding + 1 次 Milvus + 1 次 PG）

3\. 每题拿到 6 个父块 → evaluate\_case 逐块判 hit → 算出这题的 recall / precision

4\. 12 题聚合 → 3 个总指标

5\. 落库：eval\_runs 写 1 行，eval\_case\_results 写 12 行

```



\*\*预期输出（长这样）：\*\*



```

&#x20; \[OK ] q001 星云科技去年赚了多少钱 -> hits=2 780ms

&#x20; \[OK ] q002 这家公司主要是靠什么赚钱的 -> hits=1 690ms

&#x20; \[MISS] q007 前五大客户收入占比多少 -> hits=0 810ms

&#x20; ...

=== run chunk400\_top20 (a1b2c3d4) ===

&#x20; context\_recall     = 0.83

&#x20; context\_precision  = 0.71

&#x20; refusal\_rate       = 1.0

&#x20; case\_count         = 12

&#x20; avg\_latency\_ms     = 740

```



\*\*耗时：12 题 × \~0.7 秒 ≈ 10 秒。\*\*



\*\*这一跑产出的是"基线"。\*\* 基线 = 之后所有对比的参照物。



\*\*落了什么：\*\*



```

eval\_runs 一行：

&#x20; label = "chunk400\_top20"

&#x20; config\_json = {"chunk\_size":400, "chunk\_overlap":60, "top\_k":20, "final\_k":6}

&#x20; context\_recall = 0.83

&#x20; context\_precision = 0.71

&#x20; refusal\_rate = 1.0

&#x20; baseline\_run\_id = NULL        ← 这是第一次，没有基线

&#x20; run\_id, case\_id="q001", sources=\[6 个父块 JSON], metrics={"recall":1.0,"precision":1.0,...}, passed=true

```

\*\*做法 A：让脚本自己重建\*\*（跑评的时候带上参数）

\## 第 5 步：看明细，找出是哪几题挂了



\*\*总指标只告诉你"precision 掉了 6 个点"，不告诉你"哪题掉的"。\*\*



\*\*所以去查 `eval\_case\_results`：\*\*



```sql

\-- 对比两次 run 的逐题结果，找出变化的题

select b.case\_id, b.metrics->>'recall' as base\_recall, c.metrics->>'recall' as new\_recall,

&#x20;      b.metrics->>'precision' as base\_prec, c.metrics->>'precision' as new\_prec

from eval\_case\_results b

join eval\_case\_results c on c.case\_id = b.case\_id

where b.run\_id = (select id from eval\_runs where label = 'chunk400\_top20' order by created\_at desc limit 1)

&#x20; and c.run\_id = (select id from eval\_runs where label = 'chunk300\_top20' order by created\_at desc limit 1)

&#x20; and (b.metrics->>'precision')::numeric < (c.metrics->>'precision')::numeric

order by b.case\_id;

```



\*\*预期看到：\*\*



```

q006 | 1.0 | 0.33 | ...   ← "第四部分风险提示里都提了哪些风险"

```



\*\*这一题掉了\*\* —— 因为 `CHILD\_SIZE=300` 把"4.1 政策风险"和"4.2 经营风险"切得更碎，\*\*一个父块装不下两节内容，检索时只有一半命中。\*\*



\*\*这才是你要的信息。"precision 掉 6 个点"是结论，"q006 从 1.0 掉到 0.33"是原因。\*\*

\*\*看完全部明细，你面前就三种选择：\*\*



| 情况 | 决定 |

|---|---|

| 三个指标全 OK，且明细里没有明显退化的题 | \*\*保留新参数，commit\*\* |

\# 五、一次跑批内部，数据是怎么流的（你要的"链路"另一层）



\*\*上面讲的是"人怎么用"。这一层是"脚本内部怎么走"。\*\*



```

tests/eval\_cases/rag\_v1.jsonl

&#x20;      │  load\_cases()：读文件、跳过空行、json.loads → list\[dict]

&#x20;      ▼

&#x20;  12 个 dict，每条形如

&#x20;  {"id":"q001","question":"...","expected\_sections":\["2.1 营收与利润"],"expected\_keywords":\["45.6 亿"],"is\_answerable":true}

&#x20;      │

&#x20;      ▼  循环 12 次（每题一次网络三连）

&#x20;  retrieve\_sources(session, milvus, user\_id, case\["question"])

&#x20;      │    ├─ embed\_texts(\[question])         → 阿里云，1024 维

&#x20;      │    ├─ hybrid\_search(dense=\[vec], sparse=question)  → Milvus，RRF 融合

&#x20;      │    └─ batch\_get\_with\_filename(parent\_ids) → PG，取父块全文 + 文件名

&#x20;      ▼

&#x20;  每题 6 个 dict，形如

&#x20;  {"source\_id":"ref-6f798726","doc\_id":"...","clause\_name":"茅台.pdf","section\_path":"正文","content":"..."}

&#x20;      │

&#x20;      ▼  evaluate\_case(case, sources)

&#x20;  ┌─────────────────────────────────────────┐

&#x20;  │ 逐块判 hit：                              │  ← 完全没碰模型

&#x20;  │   by\_section = "2.1 营收与利润" in section\_path ?

&#x20;  │   by\_keyword = "45.6 亿" in content ?

&#x20;  │   hit = by\_section or by\_keyword

&#x20;  │                                          │

&#x20;  │ 有答案题：                                │

&#x20;  │   recall = 1.0 if any(hits) else 0.0     │

&#x20;  │   precision = 命中位置准确率的平均         │

&#x20;  │                                          │

&#x20;  │ 无答案题：                                │

&#x20;  │   recall = precision = 1.0 if len(sources)==0 else 0.0

&#x20;  └─────────────────────────────────────────┘

&#x20;      ▼

&#x20;  每题一个 metrics dict

&#x20;      │

&#x20;      ▼  aggregate(rows)：按 is\_answerable 分成两组，各自取平均

&#x20;  三个总数字

&#x20;      │

&#x20;      ├─→ EvalRepository.add\_run(EvalRun(...))      写 eval\_runs

&#x20;      ├─→ EvalRepository.add\_results(12 × EvalCaseResult)  写 eval\_case\_results

&#x20;      └─→ compare\_runs(baseline\_dict, summary) → (passed, diffs)

&#x20;               │

&#x20;               └─→ not passed → raise SystemExit(1)

```



\*\*这条链路里唯一的外部调用是 `retrieve\_sources`（每题 3 次网络往返）。判分全程零网络、零 LLM。\*\*



\*\*这就是 12 题只要 10 秒的原因。\*\*

\# 六、哪些情况你才真的会用它



\*\*说清楚"什么时候跑"，因为这是你最大的困惑点。\*\*



| 时机 | 跑不跑 | 为什么 |

|---|---|---|

| \*\*改了切分参数\*\*（`CHILD\_SIZE` / `OVERLAP` / `MAX\_PARENT\_CHARS`） | ✅ \*\*必跑\*\* | 这是这套评测唯一对准的目标 |

| \*\*改了召回参数\*\*（`top\_k` / `final\_k` / `radius`） | ✅ \*\*必跑\*\* | 同上 |

| \*\*改了 BM25 索引字段\*\*（`content` → `raw\_content`） | ✅ \*\*必跑\*\* | 你之前挂起了这个改动，真要做得先有这个才能验证 |

| 改了 prompt / 换了模型 / 改 `system\_prompt` | ❌ \*\*跑了也没意义\*\* | 这三个数字测的是检索，跟 prompt 无关 |

| 改了前端 / 改了接口格式 | ❌ | 无关 |

| 日常开发随便改改 | ❌ | 只在动检索参数时跑 |



\*\*一句话：只在"动了检索链路"的时候跑。\*\*

\# 七、为什么"给自己看"不是贬低



\*\*你现在这个状态，三个客观事实：\*\*



1\. \*\*你一个人写代码\*\* —— 没有第二双眼睛

2\. \*\*项目还没人用\*\* —— 没有用户反馈

3\. \*\*你的判断完全依赖"我记得上次好像也行"\*\*



\*\*评测填的正是这个洞。\*\*



\*\*它给你的东西只有三样，但三样都是刚需：\*\*

同一份代码跑两次，结果完全一样（`top\_k` 固定、`radius` 固定、embedding 固定的情况下）。\*\*所以"分数变了"一定是代码变了。\*\*



\*\*② 一个能对比的历史\*\*



`eval\_runs` 表里躺着 `chunk400\_top20`、`chunk300\_top20`、`chunk350\_top20`……



\*\*三个月后你打开这张表，一眼看到哪次配置最好。不用回忆。\*\*



\*\*③ 一条能说出口的依据\*\*



面试官问"你怎么评估检索质量"——



> \*\*"我有一套 12 题的回归集，覆盖口语化、术语、条款号、条件、跨文档、无答案六类。改切分参数前后各跑一次，对比 `context\_recall` / `context\_precision` / `refusal\_rate` 三个指标，任一跌超 3 个百分点脚本退出码 1。"\*\*



\*\*这句话里的每个名词都能对上你库里的表。这就是"我做过评测"和"我知道有个东西叫 Ragas"的区别。\*\*

\# 八、这套评测\*\*不管\*\*的东西（免得你误以为它万能）



\*\*明确不测：\*\*

\*\*这个边界要在文档里写清楚——面试时被追问"你的评测覆盖了哪些层"，你答"目前只覆盖检索层，生成层用 Ragas 需要裁判模型，我列为下一步"，比含糊其辞强得多。\*\*
