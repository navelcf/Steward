\## 没有 swap 时会发生什么



\*\*Linux 内存不够时，不会返回 “分配失败”，而是运行一个叫 `OOM Killer` 的机制：\*\*

1\. 内存告急

2\. 内核开始挑一个进程

3\. 挑选标准：内存占用最大的那个，优先杀

4\. 杀掉它，内存就腾出来了



\## 有了 swap 之后

\*\*swap 是硬盘上划出的一块固定大小的区域（你的 `/swapfile` 是 2 GB 的一个文件）。\*\*

\*\*当物理内存快满时，内核做的不是 “杀进程”，而是：\*\*

1\. 找一批“最近没被访问过”的内存页

2\. 把这批页的内容写到 swap 文件里

3\. 把那批物理内存页腾出来，交给正在要内存的进程

4\. 如果被搬走的那批数据，它的主人后来又用了

&#x20;  → 从 swap 文件读回物理内存



&#x09;物理内存（DDR）	swap（ESSD Entry 云盘）

访问延迟	\~100 纳秒	\~0.1～1 毫秒

带宽	20～40 GB/s	约几百 MB/s



\*\*内核任何时候都有一批 “最近没被访问的内存页”。它要决定：\*\*

> \\\*\\\*要不要主动把这些页挪到 swap 里，把物理内存腾出来？\\\*\\\*

\*\*`swappiness` 就是这个 “主动程度” 的刻度，范围 0～100。\*\*

值	行为

0	几乎不主动挪。只有物理内存真的快空了，才迫不得已挪

60（默认）	比较积极。看到一堆 “冷页” 就想挪走

100	非常积极。宁可把一堆东西塞进 swap，也要保证物理内存空闲

swap 是 “保险”，不是 “日常使用的内存”

改成 10，就是 “尽量别主动挪，但真不够了照挪不误”。

配镜像加速器

原因：Docker Hub（`registry-1.docker.io`）在国内基本拉不动，`docker pull` 会卡在 `Waiting` 或超时。

最靠谱的加速器是阿里云自己提供的：

浏览器打开：

https://cr.console.aliyun.com

左侧菜单找「镜像工具」→「镜像加速器」

页面会给你一个专属地址，长这样：

https://xxxxxxxx.mirror.aliyuncs.com

这个地址跟你的阿里云账号绑定，走内网，不计流量，速度最快。



\*\*它不是公共镜像站，而是\*\*绑定你账号的专属加速入口\*\*。\*\*

\*\*给别人看的三个风险：\*\*

\## ① 配额和带宽是共享的

\*\*加速器的吞吐额度跟你账号绑定。如果有人拿你的地址批量拉镜像，会占掉这部分额度，你自己的 `docker pull` 会变慢甚至被限流。\*\*

\*\*你不会立刻受惩罚，但会是 “莫名其妙变慢” 那种问题，很难查到原因。\*\*

\## ② 它暴露了你的账号标识

\*\*`iqvdvezi` 是阿里云按你的账号算出来的哈希。单独看它无法反推出账号，但只要结合 “这台机器公网 IP 是 47.114.112.71” 这类信息，就能把 “某个阿里云账号 → 某台 ECS” 关联起来。\*\*

\*\*面试项目如果把 `daemon.json` 传到 GitHub，就等于公开了。\*\*

\## ③ 它没有任何鉴权

\*\*这个地址不带 token、不带密码，\*\*谁拿到谁就能用\*\*。这正是它 “不应该外传” 的根本原因：它不是一个 “凭据”，而是一个 “无需凭据的通道”。\*\*

\*\*Next 会根据命令读取不同的文件：\*\*

\- `npm run dev` → 读 \*\*`.env.development`\*\*，你本地有这个文件

\- `npm run build` → 读 \*\*`.env.production`\*\*，云上必须有这个文件



从 `package.json` 看：

```

"dev":   "next dev -p 3100"      ← 开发模式

"build": "next build"             ← 编译一次

"start": "next start -p 3100"     ← 生产模式服务

```

\# `next build` 到底在做什么

\*\*它不启动服务，它是一次性编译任务。跑完进程就退出。\*\*

\*\*它做五件事：\*\*

① 静态分析：扫出所有页面路由、所有 import 关系

② 编译：把 .tsx / .ts / .css 全部编译成浏览器能执行的东西

③ 优化：tree-shaking（删掉没用的代码）、压缩、拆分 chunk

④ 替换环境变量：把 process.env.NEXT\_PUBLIC\_API\_BASE 这种

&#x20;  在代码里直接换成字面值 "http://47.114.112.71:8001"

⑤ 输出到 .next/ 目录



`next start` 到底在做什么

\*\*它启动一个服务，但做的事比 dev 少得多：\*\*

```

① 读 .next/ 目录和 BUILD\\\_ID

② 起一个极简 HTTP 服务，监听 3100

③ 收到请求 → 直接从 .next/static 里取已编译好的文件返回

④ 需要 SSR 的页面 → 调用 .next/server 里已编译好的函数

```



npm ci       → 装 500MB 依赖（你正在跑）

npm run build → 编译一次，产出 .next/（3～6 分钟）

npm run start → 起服务（只读产物，200MB）

一次性写入服务文件：

cat > /etc/systemd/system/steward-backend.service <<'EOF'

\[Unit]

Description=Steward Backend

After=network.target docker.service

Requires=docker.service



\[Service]

Type=simple

User=root

WorkingDirectory=/opt/steward

Environment="PATH=/root/.local/bin:/usr/local/bin:/usr/bin:/bin"

ExecStart=/root/.local/bin/uv run uvicorn steward.main:app --host 0.0.0.0 --port 8001

Restart=always

RestartSec=5

StandardOutput=append:/opt/steward/uvicorn.log

StandardError=append:/opt/steward/uvicorn.log



\[Install]

WantedBy=multi-user.target

EOF

然后

systemctl daemon-reload

systemctl enable steward-backend



pkill -f "uvicorn steward.main"

systemctl start steward-backend

systemctl status steward-backend





交给 systemd 管理前端。



cat > /etc/systemd/system/steward-frontend.service <<'EOF'

\[Unit]

Description=Steward Frontend

After=network.target



\[Service]

Type=simple

User=root

WorkingDirectory=/opt/steward/frontend

第二步：装 Nginx



ss -tlnp | grep ':80'

ss -tlnp 'sport = :80'# 这个精确抓



apt install -y nginx

rm -f /etc/nginx/sites-enabled/default

\*\*要确认的\*\*：`ss` 那条\*\*没有任何输出\*\*（输出为空 = 80 没人占）。如果没有输出，继续。

> 为什么删 `sites-enabled/default`：不删的话你访问 80 会看到 "Nginx 欢迎页"，而不是你的网站。





第三步：写反代配置

nano /etc/nginx/conf.d/steward.conf

粘贴这段（`Ctrl+V` 在 Workbench 里可能不生效，用右键或 `Shift+Insert`）

server {

&#x20;   listen 80;

&#x20;   server\_name 47.114.112.71;

&#x20;   client\_max\_body\_size 25m;



&#x20;   location /api/ {

&#x20;       proxy\_pass http://127.0.0.1:8001;

&#x20;       proxy\_http\_version 1.1;

&#x20;       proxy\_set\_header Host $host;

&#x20;       proxy\_set\_header X-Real-IP $remote\_addr;

&#x20;       proxy\_set\_header X-Forwarded-For $proxy\_add\_x\_forwarded\_for;

&#x20;       proxy\_set\_header Connection "";

&#x20;       proxy\_buffering off;

&#x20;       proxy\_cache off;

&#x20;       proxy\_read\_timeout 600s;

&#x20;   }



&#x20;   location / {

&#x20;       proxy\_pass http://127.0.0.1:3100;

&#x20;       proxy\_http\_version 1.1;

&#x20;       proxy\_set\_header Host $host;

&#x20;       proxy\_set\_header Upgrade $http\_upgrade;

&#x20;       proxy\_set\_header Connection "upgrade";

&#x20;       proxy\_read\_timeout 600s;

&#x20;   }

}



\- `proxy\_pass http://127.0.0.1:8001;` \*\*结尾不能加斜杠\*\*。加了 `/` 会把 `/api/` 前缀吃掉，变成 `/v1/auth/login`，后端 404。

\- `proxy\_buffering off;` 只写在 `/api/` 里。不写这一行，你的\*\*流式回答会变成一次性蹦出来\*\*。





nginx -t \&\& systemctl reload nginx

\*\*要确认的\*\*：输出 `syntax is ok` + `test is successful`。报错就去改，别继续





第四步：前端改成 "同源"，重新 build

这是\*\*唯一需要重新编译\*\*的一步，原因是 `NEXT\_PUBLIC\_\*` 在 build 那一刻就被写死进 JS 文件了。

cd /opt/steward/frontend

sed -i 's|^NEXT\_PUBLIC\_API\_BASE=.\*|NEXT\_PUBLIC\_API\_BASE=|' .env.production

cat .env.production



\*\*要确认的\*\*：文件里是 `NEXT\_PUBLIC\_API\_BASE=`，等号后面空白

npm run build



\*\*为什么这样就对了\*\*：你前端 `lib/api.ts` 第 17 行写着 —— 生产环境没配时回落到空串，注释原话是 "走同源（通常由 nginx 把 /api 反代到后端）"。\*\*等于这个前端本来就是为反代设计的\*\*，你只是把之前写死的 `http://47.114.112.71:8001` 去掉。

改完以后所有请求变成 `/api/v1/...` \*\*相对路径\*\* → 自动打到当前页面所在的 80 端口 → Nginx 分流。好处是：以后无论用 IP 还是 Cloudflare 域名访问，都不用再 build（相对路径跟着当前页面走）。
