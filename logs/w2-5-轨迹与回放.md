次对话从开始到结束，走一遍：

① event\_stream 开头

&#x20;  collector = TraceCollector(run\_id, user\_id, thread\_id, base\_step)



② 模型调用开始

&#x20;  → collector.begin(evt\_run\_id\_1)

&#x20;  → \_started = {evt1: 123456.78}



③ 模型调用结束

&#x20;  → latency = collector.end(evt\_run\_id\_1)          # 算出 1200ms

&#x20;  → collector.add(kind="model", name="deepseek-flash",

&#x20;                  latency\_ms=1200, prompt\_tokens=800, completion\_tokens=120)

&#x20;  → \_step 变成 1，\_rows 有 1 行



④ 工具调用开始

&#x20;  → collector.begin(evt\_run\_id\_2)

&#x20;  → collector.remember\_tool(evt\_run\_id\_2, "save\_note", {"content": "..."})



⑤ 工具调用结束

&#x20;  → latency = collector.end(evt\_run\_id\_2)          # 算出 5ms

&#x20;  → name, args = collector.pop\_tool(evt\_run\_id\_2)

&#x20;  → collector.add(kind="tool", name="save\_note",

&#x20;                  input=args, output="4/xxx.md", latency\_ms=5)

&#x20;  → \_step 变成 2，\_rows 有 2 行



⑥ 模型再调一次（说「已保存」）

&#x20;  → 又是 begin / end / add

&#x20;  → \_step 变成 3，\_rows 有 3 行



⑦ 流结束

&#x20;  → await collector.flush(factory)

&#x20;  → 3 行一次性 commit 进数据库









LangGraph 的执行方式是「超级步」（super-step）：

节点 A 跑完 → 存一张 checkpoint

节点 B 跑完 → 再存一张

节点 C 跑完 → 再存一张



每张 checkpoint 里都有：

字段	内容

values	那一刻所有状态，比如 messages 里有哪些消息

next	下一步该跑哪个节点（空元组 = 结束了）

tasks	待执行的任务，中断时这里有 interrupts

metadata	步号、来源节点等

snapshot = await agent.aget\_state(config)      # 调出最新那张照片

pending = \[item for task in snapshot.tasks for item in task.interrupts]   # 看照片里有没有"待办中断"





事件流：

{

&#x20;   "event": "on\_chat\_model\_start",      # ① 事件类型

&#x20;   "name": "ChatOpenAI",                # ② 组件名

&#x20;   "run\_id": "6f2a9c1e-...",            # ③ 这次调用的 uuid

&#x20;   "parent\_ids": \["8b3d..."],           # ④ 父调用链（暂时可以不看）

&#x20;   "tags": \[],

&#x20;   "metadata": {"langgraph\_node": "model", "langgraph\_step": 1},

&#x20;   "data": {"input": {...}},            # ⑤ 真正的内容

}



事件名	什么时候

on\_chain\_start / on\_chain\_end	节点（graph /model 节点 /tools 节点）开始 / 结束

on\_chat\_model\_start	模型开始调用

on\_chat\_model\_stream	模型吐一个 token chunk（一堆一堆的）

on\_chat\_model\_end	模型说完

on\_tool\_start	工具开始执行

on\_tool\_end	工具执行完

on\_retriever\_start / on\_retriever\_end	检索（P2 做 RAG 才会出现）







字段	干什么	你代码里用了吗

event	事件类型，决定你这行代码走哪个分支	✅ kind = event\["event"]

name	组件名。模型事件是类名，工具事件是工具名	✅ 工具名从这拿

run\_id	这次调用的 uuid，用来配对 start 和 end	✅ key = event\["run\_id"]

parent\_ids	父节点链，画调用树用的	❌ 没用，P1 不需要

metadata	元信息（哪个节点、第几步）	❌ 没用（langgraph\_step 恢复后会从 1 重来，所以不用）

data	内容。start 时是 input，stream 时是 chunk，end 时是 output	✅ 全靠它



&#x09;是什么	谁给的

event\["run\_id"]	一次调用的编号。模型调用一次、工具调用一次，各一个	LangChain 事件

run\_traces.run\_id	一次任务的编号。整次对话，从用户发消息到回答结束，一个	你生成的 uuid

有个bug：

卡过期后 `status` 变成 `expired`，但 checkpointer 里的 pending interrupt \*\*还在\*\*。用户发新消息，照样 400。

\# 过期 + checkpointer 还挂着 ——\*\*这是个死结，现在必崩\*\*



\*\*完整链条：\*\*



```

1\. 24 小时前建了一张卡，checkpointer 里挂着 \_\_interrupt\_\_，next=('tools',)

2\. 24 小时后用户发新消息

3\. /chat/stream 不检查（现在没有这个检查）

4\. agent 从旧状态继续 → assistant(tool\_calls) 后面缺 tool 消息

5\. DeepSeek 400 → SSE 推 error「生成失败，请稍后重试」

6\. 用户完全不知道发生了什么，卡也永远批不了（一批准就 409 过期）

```



\*\*这张卡实际上\*\*废了\*\*：审批失败，聊天也失败。\*\* 用户唯一的出路是删掉这个会话。



\## 三个解法，按成本排



\### 方案 A：入口惰性清理（最实用）



在 `/chat/stream` 进入 `event\_stream` 之前，查这个 thread 的卡：



```

pending = await ApprovalRepository(session).list\_by\_thread\_status(

&#x20;   thread\_id, user\_id, ("pending", "expired")

)



for card in pending:

&#x20;   expired = card.expires\_at and datetime.now(UTC) > card.expires\_at

&#x20;   if expired or card.status == "expired":

&#x20;       # ① 落 expired（幂等，CAS 已在，重复落不会错）

&#x20;       # ② 用 Command(resume={interrupt\_id: {"type": "reject", "message": "审批已过期，自动取消"}})

&#x20;       #    静默跑一遍 agent，不推事件给前端 —— 这样 pending 被消费，历史补上 tool 消息

&#x20;       await \_consume\_interrupt\_expired(...)

&#x20;   else:

&#x20;       raise HTTPException(409, "这个会话有待处理的审批，请先批准或拒绝")

```



\*\*代价：过期卡第一次触发时多跑一次模型调用（几十 token）。\*\*



\*\*收益：\*\*



\- \*\*过期卡变成 reject，模型收到「用户拒绝」的 ToolMessage，历史闭合\*\*

\- \*\*用户发新消息正常回答\*\*

\- \*\*不需要后台任务，不需要动 checkpointer 的表\*\*



\*\*「静默跑一遍」这个动作有没有副作用？\*\* 会产生一条 assistant 消息（模型说「好的，那我不记了」），\*\*这条可以顺手落进 `messages` 表\*\*—— 用户下次看历史会看到「审批已过期，已自动取消」。\*\*反而是好事。\*\*



\### 方案 B：建卡不设过期



`CARD\_TTL` 改无限。\*\*过期的洞直接不存在。\*\*



\*\*代价：\*\* 用户可以三天后批一张卡，而模型上下文早就换了，工具参数可能已过时。\*\*教程设 24 小时就是为了兜这个。\*\*



\### 方案 C：后台定时扫描



`lifespan` 里起 `asyncio.create\_task`，每分钟扫过期卡 + 消费中断。



\*\*问题：\*\*



\- 要拿 `agent`（但 `build\_agent` 是每请求构造的，后台任务得自己构造一份）

\- \*\*用户不在的时候跑模型，烧 token\*\*

\- 还要处理「跑出来的 assistant 落不落库」



\*\*复杂度是方案 A 的 5 倍，收益几乎为零\*\*（用户不在，清不清都无所谓，来了再清就行）。



\## 我的建议



\*\*采用方案 A，分两步做：\*\*



\*\*第一步（10 分钟，今天就能做）：只管「有卡就 409」\*\*



```

\# chat/deps.py

async def assert\_no\_pending\_approval(thread: ChatThread = Depends(get\_owned\_thread), ...):

&#x20;   n = await ApprovalRepository(session).count\_pending(thread.id, thread.user\_id)

&#x20;   if n:

&#x20;       raise HTTPException(409, "这个会话有待处理的审批，请先批准或拒绝")
```
